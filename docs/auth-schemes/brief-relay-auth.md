# 中继鉴权方案探索总纲（brief-relay-auth）

> 背景：模型 API 中继（/relay，本机 9850）当前用「/relay/token 签发一次性票据」做访问控制，但 /relay/token 自身无权限校验，任何人可取票——被用户指出是错误设计。需要**架构级正确、生产可用**的方案，不打补丁。

## 目标

1. 中继只允许「已登录用户经本应用页面发起」的请求；未登录或外部直接 curl 一律拒绝。
2. 方案必须是架构级设计（不是再加一层补丁），考虑：票据/会话绑定、同源反代、总线签发、生产部署形态（内网穿透/反向代理）下的正确性。
3. 不破坏现有能力：登录后真实对话、流式、中断、多轮都必须继续工作。

## 三条探索路线（3 个方案代理各认领一条）

| # | 代号 | 核心思路 |
|---|------|----------|
| R1 | 会话 Cookie 绑定 | 中继校验「登录会话 Cookie」（HttpOnly + SameSite），登录时由 auth 插件种 cookie；中继与页面同源（经反代），cookie 自动携带，前端无需传票 |
| R2 | 反代同源 + 宿主内嵌 | 取消独立 9850 中继进程，把中继作为宿主 HTTP 服务（vite/生产 server）的内置路由，天然同源 + 复用宿主登录态中间件 |
| R3 | 总线签发短期令牌 | 登录后由 auth 插件经总线签发「中继访问令牌」（短时效、绑定会话），引擎每次调用前换取；中继校验令牌与登录态绑定 |

## 评分维度（2 评委）

- A 安全正确性 40%（未登录/外部 curl 确实被拒；无绕过面；凭据不泄露）
- B 架构正确性 30%（是否治本、是否依赖部署巧合、生产形态是否成立）
- C 可实现性与兼容 20%（改动面、现有流式/中断/多轮是否不受影响）
- D 简洁性 10%（机制是否简单可靠，避免过度设计）
