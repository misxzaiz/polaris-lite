# 权限验证插件工作流总纲（brief-auth）

> 目标：为 polaris-lite 增加「权限验证」能力，**必须以外部插件实施**（与宿主零源码耦合），且**支持替换插件**（同一能力契约可换不同实现）。

## 一、用户目标拆解

1. **权限验证插件**：提供登录/身份验证 + 权限校验能力（例如：页面访问前需登录；不同角色可访问不同面板）。
2. **插件实施**：宿主不写死任何权限逻辑；权限验证是一个外部插件（与 chat-lite/real-engine 同形态：独立构建 + registry.json 注册 + 运行时动态加载）。
3. **可替换**：定义清晰的契约（如 `cap.auth`），任何满足契约的插件（本地账号密码、OAuth、LDAP、企业 SSO……）都可以互相替换，宿主与业务插件零改动。
4. **多 agent 工作流**：3 个方案代理并行设计不同路线 → 2 个评委代理交叉评审打分 → 选出冠军方案 → 实施。

## 二、能力契约（所有方案必须遵守）

- 新增能力 id：`cap.auth`（provides 由权限插件声明）。
- 最低动作集（引擎/面板等调用方按需声明 `capabilities: ['cap.auth']`）：
  - `status` → 当前登录状态（是否已登录、用户名/角色、token 摘要）
  - `login(payload)` → 登录（凭据形态由插件自定义，如用户名密码）
  - `logout()` → 登出
  - `check(permission)` → 校验某权限是否通过
- 权限插件可以提供 UI 槽位贡献（如全屏登录覆盖层）或纯 headless（由宿主壳读取 status 决定是否放行渲染）。

## 三、硬性约束

1. 宿主源码（src/）**不得出现任何具体权限插件的引用**；一切经 registry.json + 动态加载。
2. 未登录时的行为：四槽壳仍可渲染，但业务面板/对话是否放行由权限插件的能力决定（方案需明确策略）。
3. 支持替换：mock-auth（演示用，任意账号可登录）与真实实现可经 registry.json `enabled` 切换。
4. 与现有 cap 总线一致：权限插件经 `registerCapability` 注册，受 `provides` 校验。

## 四、方案差异化矩阵（3 个方案代理各认领一格）

| # | 代号 | 路线 |
|---|------|------|
| P1 | 壳层拦截 | 宿主壳（SlotLayout）读 cap.auth status，未登录渲染登录槽；纯 headless 契约 |
| P2 | 覆盖层插件 | 权限插件自带全屏登录 UI（overlay），自己控制拦截与放行；宿主只提供覆盖层挂载点 |
| P3 | 路由/角色矩阵 | 插件维护「角色→可用面板/能力」矩阵，check(permission) 细粒度控制每个槽位/Tab 的可见性 |

## 五、评分维度（2 评委）

- A 目标符合度（契约清晰、可替换性、插件化程度）40%
- B 具体可实现性（能直接开工）30%
- C 体验与安全（登录流程、token/凭据处理、失败路径）20%
- D 对现有架构的侵入度（越低越好）10%
