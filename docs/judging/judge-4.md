## 最推荐方案：S02 契约优先

**理由（安全与运行时治理视角）**：

1. **权限与审计真实且默认拒绝**：PolicyEngine 以 manifest.caps 允许表做默认拒绝裁决，每笔 dispatch 落 JSONL 审计，总线是唯一通道——cap 总线的治理语义被完整保留，同时从 1.8k 行裁到约 400 行，审计与权限不再被业务复杂度淹没。
2. **核心小到可以被完整审计**：核心约 9k 行，安全审查可以逐行完成；这对"轻量版"是比行数数字更重要的治理收益——信任根足够小。
3. **对已知风险的处置最成体系**：契约单源（JSON Schema + Rust/TS 双端一致性 CI）正面补上"协议无运行时校验"缺口；中断按 sessionId 精确取消 + 晚到事件丢弃，明确吸取 Polaris 中断链路教训；插件加载限定白名单目录 + prod 自定义协议，杜绝任意路径装载。
4. **扣分项可控且可补**：sidecar 端口鉴权与 UI 插件进程隔离是它的两个真实缺口，但两者都可以在不推翻架构的前提下补齐（sidecar 加 loopback token / unix pipe；UI 插件后续升级 worker/进程隔离）——相比之下 S4 的同进程同特权是形态级缺陷，S7 的主仓改写是约束级违规。

**备注**：若把"插件隔离强度"列为第一优先，S10 是最稳的替代（唯一提供真实进程级隔离与不可伪造 origin 的方案），建议作为 S2 落地后的安全增强演进方向；S7 工程质量与风险披露均属上乘，排名垫底仅因实施路径与 brief P8 独立性硬约束直接冲突。
