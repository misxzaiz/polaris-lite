# 评委1评分表

> 评审视角：**工程落地可行性**——方案能否直接开工、契约是否可执行、迁移步骤是否可信。
> 评分依据：`docs/brief.md`（P1~P8 + 硬性约束 1~7）与 `docs/baseline.md`（Polaris 事实基线）。
> 权重：A 目标符合度 30% / B 具体可实现性 25% / C 轻量收益 20% / D 架构优雅可维护 15% / E 迁移成本与风险 10%。总分 = Σ(维度分×权重)，百分制。

---

## S1 微核直译（复制 Polaris 壳 + 删业务 + Chat 树打包为内置插件）

| 维度 | 得分 | 简评 |
|---|---|---|
| A 目标符合度 | 7.5 | 布局不变、UI 插件化、独立建仓、cap 总线保留均达标；但核心保留 `proxy`(5.0k) 与完整 `ai_chat_core`，按 baseline §7 口径 proxy 属业务域，P4「核心零业务」打折扣 |
| B 具体可实现性 | 9.0 | 全部契约照抄 Polaris 现行签名，目录/启动/挂载链路逐行可查，"删除劳务 + 打包接线"性质，今天就能开工 |
| C 轻量收益 | 6.5 | 核心 55k 行（-64%）真实但幅度十案中偏小，且把 proxy 一并保留进一步稀释了"轻" |
| D 架构优雅可维护 | 6.5 | 原样继承 plugin-system 与 Blob 加载器，边界与 Polaris 现状相同，只做了 appCoreBridge 收窄；长期演进跟随 Polaris 债务 |
| E 迁移成本与风险 | 9.0 | 2~4 人周估算可信，风险表把"Chat 树依赖闭包""白名单收窄"两个真坑摆在最前面，诚实度高 |
| **加权总分** | **76.8** | |

**评语**：十案中开工成本最低、行为一致性最高的一案，契约全部是已验证的现行实现，"复制+删除+打包"的路径没有任何想象成分。它的价值在于把 polaris-lite 的下限抬得很稳：只要 Polaris 能跑，lite 第一版就能跑。适合作为"先有一个能用的 lite"的保底路线。

**最大缺陷**：核心保留了 proxy 与过重的 ai_chat_core/storage_exec（合计 ~13k 行业务色代码），"核心零业务"是靠解释而非靠结构达成的——若评审从严，S1 的终点更像"小号 Polaris"而非"零业务微核"。

## S2 契约优先（重写极薄核心 + 最小贡献契约）

| 维度 | 得分 | 简评 |
|---|---|---|
| A 目标符合度 | 8.5 | 核心只留总线+生命周期+6 个通用 cap，对话四段式整体归 chat-desk 插件，main 席位唯一性有硬校验，P4/P5 满足度最高档 |
| B 具体可实现性 | 7.5 | manifest/CapBus/HTTP 代理协议三层契约都到了可开工粒度，P0~P8 里程碑带验证门槛；但 chat-desk UI 全量重写（11k 行）+ ai-engine sidecar 新写（2.2k 行）是两块硬骨头 |
| C 轻量收益 | 8.5 | 核心 ~9k 行（6%）、总量 -83%，量化口径清楚；chat-desk 23.7k→11k 的瘦身有裁剪范围支撑 |
| D 架构优雅可维护 | 8.5 | 契约先行 + 默认拒绝权限 + JSONL 审计，边界干净；manifest 砍到 4 类贡献点，长期演进要靠扩契约 |
| E 迁移成本与风险 | 6.0 | 本质是"重写派"，引擎/MCP/多会话等 Polaris 能力首版不保，对依赖这些能力的用户是功能回退；风险披露如实但工作量大头在写新代码 |
| **加权总分** | **80.0** | |

**评语**：如果目标是"设计一个配得上 lite 之名的最小平台"，S2 是答案——契约面小到可以背下来，权限/审计/转发语义完整，且明确吸取了 Polaris 中断链路的教训（按 sessionId 精确取消、晚到 delta 丢弃）。它的执行力风险不在架构而在工作量：对话 UI 与 AI 引擎两块都要重写。

**最大缺陷**：把 `ai_chat_core`(3.0k)+`simple_ai`(10k) 压缩成 2.2k 行 sidecar 的假设过于乐观——工具调用、附件、plan 模式、供应商 failover 这些被砍掉的能力，恰恰是 Polaris 对话体验的护城河，首版可用的"轻"可能以功能塌方为代价。

## S3 插槽容器（核心 = 四槽布局壳 + 槽位注册制）

| 维度 | 得分 | 简评 |
|---|---|---|
| A 目标符合度 | 8.5 | 四槽与 Polaris 四段式一一对位，布局不变性由 SlotLayout 复制现役样式 + DOM 快照锁定；核心零业务有 eslint + Rust 目录守卫双闸，是唯一把"白名单"做成 CI 门禁的方案 |
| B 具体可实现性 | 8.0 | SlotRegistry/SlotHostApi/manifest s3.1/Rust 总线签名齐全，M0~M6 每步有验收；chat 树去宿主耦合约 15~20 文件、3~5 天的预估量级合理 |
| C 轻量收益 | 8.0 | 核心 ~15.5k 行（10%），裁剪表按域列明来源与去向，可信 |
| D 架构优雅可维护 | 8.0 | 槽位注册制 + 最小 SlotHostApi 取代 21-store 泄漏，模型简单、表达力边界明确（SLOT_ARITY 可扩展），single/stack 仲裁规则确定性 |
| E 迁移成本与风险 | 7.5 | 复制+裁剪为主、无框架切换；风险表对"chat 树残留宿主耦合""调度壳过薄"有实招 |
| **加权总分** | **81.0** | |

**评语**：S3 是"架构边界"与"工程可执行"之间平衡最好的方案：核心退化为插线板（四槽 + 一条总线），对话与业务全部插件化，且用 CI 门禁把核心零业务从口号变成可断言的验收项。它没有 S2 那样激进的契约重写，也没有 S1 那样重的核心，复制 Polaris 已验证件（transport/theme/loader/RouterBus）的比例高，开工路径清晰。

**最大缺陷**：sidebar/stream/input 三个 single 槽被 chat-desk-lite 独占后，多会话网格、双对话并排等 Polaris chat-desk 增值形态在四槽模型内无法表达，只能靠"新增槽位改核心"解决——表达力天花板写在架构里。

## S4 Web-Only 单进程（砍 Tauri，Node/Bun + HTTP/SSE 总线）

| 维度 | 得分 | 简评 |
|---|---|---|
| A 目标符合度 | 8.0 | 布局四段式由核心壳 + chat-lite 插件保持，cap 总线以 HTTP dispatch + SSE 落地且"除静态资源外无业务 REST 路由"的纪律很好；砍掉桌面形态是本格矩阵授权的取舍，但相对"参考 Polaris"的桌面产品身份是一次更大的偏移 |
| B 具体可实现性 | 8.5 | HTTP API 表、SSE 事件契约（seq 续传/心跳）、TS 版 RouterBus、zod 双端校验、启动序列全部到可开工粒度；Polaris 已有 `web/api/ipc.rs` HTTP 桥先例，技术选型无悬念 |
| C 轻量收益 | 9.0 | Rust -100%、核心 ~10.5k 行 TS，砍掉整个 Cargo/feature 门控/MSI 工具链，是十案中"轻"得最干净、最可验证的一案 |
| D 架构优雅可维护 | 7.5 | 两层进程模型 + 单一总线入口清晰；但插件同进程无隔离（自认）、SSE 长连接管理、单点故障域是长期运维债 |
| E 迁移成本与风险 | 7.0 | 后端总线/插件机制为 TS 重写，chat 面板只搬四段式必需子树；桌面能力全弃已如实写入非目标，风险评估（SSE 工程、中断语义、鉴权）专业 |
| **加权总分** | **81.5** | |

**评语**：从纯工程落地看，S4 的确定性最高：没有 Rust 编译链、没有 feature 门控陷阱、没有 Tauri DLL 限制，`pnpm dev` 秒级起，量化表几乎每一项都能用 cloc/计时实测复核。SSE + Last-Event-ID 续传、interrupt 幂等、zod 协议校验这些细节说明作者真的考虑过生产化。代价是它交付的是一个"Web 应用"而非"桌面应用"。

**最大缺陷**：彻底放弃桌面形态（托盘/自启/自动更新/原生窗口/离线安装包），而 Polaris 的产品身份是桌面 AI 工作台——若 lite 需要保持与 Polaris 同类的交付形态，S4 还要再补一层 Tauri/Electron 壳，届时"砍 Tauri"的核心收益会被部分吃掉。

## S5 微前端（Module Federation 运行时）

| 维度 | 得分 | 简评 |
|---|---|---|
| A 目标符合度 | 7.5 | 布局/插件化/独立建仓达标，cap 总线原样继承；但 Rust 侧仍保留 ai_chat_core + 引擎（6k 行），核心业务色与 S1 同病 |
| B 具体可实现性 | 7.0 | federation 配置、契约包、生命周期协议、CI 护栏都写了；但 `@originjs/vite-plugin-federation` 维护活跃度存疑（作者也备了 webpack 退路），8 个 remote 多端口编排的日常开发成本不低 |
| C 轻量收益 | 7.0 | 核心 ~41.5k 行（-73%），首屏懒加载收益真实；但为单用户桌面工具引入微前端的复杂度税没有体现在收益表里 |
| D 架构优雅可维护 | 6.5 | 构建期联邦替换 Blob 字符串手术是真实进步，但 shared 依赖版本协商、remoteEntry 分发、契约版本握手都是长期维护面 |
| E 迁移成本与风险 | 6.5 | 10~13 人日偏乐观（8 个 remote 改造 + chat-desk 剥 21-store 依赖）；共享依赖双实例风险有专项对策，披露诚实 |
| **加权总分** | **70.3** | |

**评语**：S5 对 Polaris Blob-URL 加载器缺陷的诊断（正则改写错位、双实例、vendor 上限）非常准确，用构建期联邦替代运行时字符串手术的方向正确。但它把"多团队独立部署微前端"的解法搬到了单人本地工具场景，收益主要剩下"加载机制更正规"，与付出的联邦复杂度不成比例。

**最大缺陷**：为解决一个 155 行加载器的问题引入了一整套微前端运行时（8 个独立构建目标、shared 依赖治理、remoteEntry 分发、contract 版本协商）——用大炮打蚊子，且 `@originjs/vite-plugin-federation` 的社区维护状态是悬在方案头上的第三方风险。

## S6 Web Components（核心零框架，插件 = 自定义元素）

| 维度 | 得分 | 简评 |
|---|---|---|
| A 目标符合度 | 7.5 | 核心零框架零业务、混栈插件、cap 总线保留，P5 的"框架无关"路线执行得最彻底；布局四段由插件内部元素组合实现，宿主只给 main.surface 槽 |
| B 具体可实现性 | 6.0 | PolarisContext/命名规范/事件契约清楚，但把 23.7k 行 React chat-desk 重写为 ≤6k 行 wc（Lit/vanilla）是十案中最大的单点重写；React↔wc 互操作（属性只认 string、合成事件不进 shadow、复杂对象走 property）会持续消耗工时 |
| C 轻量收益 | 6.5 | 核心前端 ≤9k 可信，但 Rust 仍保留 55k（-46%），整体裁剪幅度中等 |
| D 架构优雅可维护 | 7.0 | 契约级解耦（attributes/events/DOM）理论上最稳，但 wc 生态基建（虚拟列表、表单、markdown 流式渲染）弱于 React，这些都要自建，长期是隐形负债 |
| E 迁移成本与风险 | 5.5 | "React in wc"渐进包装能降低风险，但等于先包一层再逐个换，两套范式长期并存；风险表诚实承认这是最大成本 |
| **加权总分** | **66.5** | |

**评语**：S6 在理念上最"正确"——用浏览器原生协议做插件边界，核心连 React 都不认识。但工程现实是：Polaris 的对话 UI 是重 React 资产（104 文件 26.9k 行的 Chat 树、23.7k 行的 chat-desk），wc 化重写等于放弃这笔资产的全部复用价值，而换来的"混栈能力"并不是本项目任何一条硬性需求。

**最大缺陷**：为框架无关的纯粹性支付全量 UI 重写成本，而项目约束里没有任何一条要求"插件必须用不同框架"——收益与成本严重错配，且 chat 消息流所需的虚拟滚动/流式 markdown 在 wc 生态里恰恰是最不成熟的领域。

## S7 渐进剥离（在 Polaris 主仓上分阶段瘦身至 lite）

| 维度 | 得分 | 简评 |
|---|---|---|
| A 目标符合度 | 6.0 | 终点形态（席位壳 + 插件体系 + 20 个通用 cap）本身合规；但作业方式是在 Polaris 主仓开 `feat/polaris-lite` 长驻分支并逐批合回 main，直接抵触 brief P8"不修改 Polaris 主仓任何文件、代码放在 Polaris-lite 独立目录"的硬约束 |
| B 具体可实现性 | 9.0 | 全部清单带实测行数与去向，验收标准 V1~V7 可执行，复用已在跑的 core-slimdown 工程，每批可回滚——这是十案中"明天就能派工"程度最高的一份 |
| C 轻量收益 | 6.5 | 保守口径 -44%（85k）、目标口径 -75%（38k），且终点仍保留 Polaris 的 Blob 加载器、appCoreBridge（收窄版）等历史结构，"轻"得不够彻底 |
| D 架构优雅可维护 | 6.0 | 不变式守护得好（cap/事件/manifest 不动），但终点架构 = Polaris 现状减业务，21→8 store、30→12 白名单只是收窄而非重构，历史包袱全部继承 |
| E 迁移成本与风险 | 8.0 | 迁移风险确实最低（每步踩在已验证套路上）；但"与主仓演进冲突"被作者自己列为高风险，lite 的独立性始终受主线引力牵制 |
| **加权总分** | **70.5** | |

**评语**：作为一份工程执行清单，S7 几乎无可挑剔：文件级清单、行数对账、双端门禁、回滚预案、阶段冒烟一应俱全，且建立在已经发生的事实（git/browser/IM 等域已出仓、chat-desk 已接管）之上。问题在于它对"polaris-lite 是一个独立新仓"这一定位理解成了"主仓的终局形态"，与 brief 的 P3/P8 存在根本冲突。

**最大缺陷**：违反 P8 硬约束——它的全部工作发生在 Polaris 主仓内并合回 main，产物不是 `D:\space\base\Polaris-lite` 里的独立可构建仓库；按 brief 口径，这份方案的交付物更像"主仓瘦身计划"而非"lite 实现方案"。

## S8 事件溯源微核（EventLog + 投影插件）

| 维度 | 得分 | 简评 |
|---|---|---|
| A 目标符合度 | 8.0 | 核心 = 日志 + 总线 + 壳，业务全为投影插件，dispatch 入日志使"总线审计"与"事件溯源"合一，四段式由 chat-projection 内部对齐；约束满足度好 |
| B 具体可实现性 | 6.5 | 事件 schema/Projection/checkpoint 契约写得非常细，但 EventLog 后端、前端 ProjectionKernel、checkpoint 存储全是新增基础设施（~2.5k 行新代码），且 ai_chat_core 的 plan/attachments/供应商路由首版全部舍弃——可用性验证周期最长 |
| C 轻量收益 | 8.0 | 核心 ~1 万行、storage_exec + conversationStore(16k 行) 被日志+投影整体替代，裁剪逻辑自洽 |
| D 架构优雅可维护 | 8.5 | 单写者、纯函数投影、checkpoint 有界重放、时间旅行调试——十案中架构一致性最高的设计；但 upcaster/三段版本号是长期的认知税 |
| E 迁移成本与风险 | 5.0 | 等于把会话状态管理从零再造一遍；流式 delta 每 token 一事件、万级会话的日志膨胀、投影 stateVersion 升级触发全量重放，都是上线后才暴露的坑 |
| **加权总分** | **74.0** | |

**评语**：S8 是十案中思想最完整的一案：把 session-v2 的"日志即真相"从会话域推广到全应用，审计链、对账、回放、调试全部统一到一条事件流上，契约文本的质量也是最高的。作为架构提案我愿意给它高分；但作为"要落地的 lite"，它要求团队先建造事件溯源基础设施，再在之上重写对话域，交付周期与行为回归风险都是十案中最高的。

**最大缺陷**：核心基础设施（EventLog/ProjectionKernel/checkpoint/Upcaster）全部为新造轮子，且 AI 对话这种"高频流式 delta + 大状态 + 强交互"场景恰恰是事件溯源最昂贵的应用场景——性能与复杂度风险集中爆发在项目最关键的链路上。

## S9 Vite 模板（脚手架 + npm 插件包 + 构建期集成）

| E 迁移成本与风险 | 7.0 | 复制壳 + TS 重写总线 + 裁剪 chat-desk，工作量中等；"模板腐化""pnpm 扫描漏包"等风险有具体对策 |
| **加权总分** | **78.5** | |

**评语**：S9 是对 Polaris 插件加载痛点（无类型、无摇树、双实例、沙箱伪装）回应得最"前端正统"的方案：插件即 npm 包，集成发生在构建期，一切用现成工具（Vite/pnpm/plop/semver）解决。它对"运行时动态性损失"的披露非常坦率，并用 `polaris add` 一条命令 + dev HMR 监听把体验落差压到可接受。唯一要问的是：lite 是否需要"应用运行中热装插件"——若不需要，S9 的取舍几乎无代价。

**最大缺陷**：放弃运行时插件安装是产品能力的实质收缩——Polaris 现有 150+ 插件的分发/热装生态无法直接迁入，所有插件必须以 npm 包形态重新发包并随构建集成；对既有插件资产而言，这是一次断裂式迁移。

## S10 桌面双进程（Rust 极简壳 + Node 插件宿主 + 渲染指令协议）

| 维度 | 得分 | 简评 |
|---|---|---|
| A 目标符合度 | 8.0 | 三进程职责表清晰，cap 裁决/审计收口在壳、业务全在宿主进程插件、四段式布局保留；"核心零业务"以物理隔离方式达成，最彻底 |
| B 具体可实现性 | 6.0 | IPC 帧/方法表/事件主题/权限表/生命周期状态机写得极细，但对话 UI 要经由受控 UINode 指令树 + diff 下发来重建——气泡、工具卡、流式 markdown、虚拟滚动全部要在这套受限原语上重新实现，工程量与体验风险都很大 |
| C 轻量收益 | 7.0 | 核心 ≤19.5k 行（13%），但 Node 宿主常驻 40-80MB 内存 + 进程启动开销，"轻量"被部分抵消（作者已诚实标注） |
| D 架构优雅可维护 | 6.5 | 物理切除 appCoreBridge 是真解耦；但渲染指令协议是一个需要长期演进的自研 DSL，表达力天花板（作者自己预留了 html 白名单二档）说明协议会不断被业务倒逼扩张 |
| E 迁移成本与风险 | 5.0 | IPC 延迟、进程管理、chaos 恢复、协议双端镜像，每项都要专项建设；simple_ai 万行引擎在 Node 侧重写的估工（≤2.5k 行）明显偏乐观 |
| **加权总分** | **67.8** | |

**评语**：S10 把 Polaris 最深的耦合点（同窗 Blob 加载 + 21 store 共享）用进程边界物理切断，思路的彻底性值得尊敬，IPC 协议文本的完备度也是十案最高之一。但它要求同时建成：跨进程 JSON-RPC 总线、进程守护、受控 UI 原语集、diff 渲染协议、双端类型镜像——这几乎是一个新的前端框架加上一个 IPC 框架的工作量，而目标只是让对话面板"看起来和 Polaris 一样"。

**最大缺陷**：自研渲染指令协议（UINode + diff）是隐藏在方案里的最大工程黑洞——Polaris 对话 UI 的全部表现力（富文本气泡、工具卡片、动态表单、图表）都要压缩进十来种受限节点，要么协议无限膨胀，要么 UI 大幅降级；这是典型的"为解耦引入新框架"陷阱。

## 我个人最推荐：S3 插槽容器

理由（从工程落地可行性出发）：

1. **今天就能开工，且每一步都在已验证的地面上**。S3 的核心件（RouterBus 裁剪、transport、themeEngine、pluginModuleLoader、Common 组件）全部从 Polaris 现行代码复制，对话 UI 从 worktree Chat 树按槽拆入——没有一块需要"先发明再验证"的基础设施。对比 S8（要先造 EventLog/ProjectionKernel）和 S10（要先造 IPC 框架 + 渲染指令协议），S3 的第一周就能看到四槽壳亮起来。

2. **契约到了签名级，且配套了可执行的守卫**。SlotRegistry/SlotHostApi/manifest s3.1/Rust Capability 签名齐全之外，S3 是唯一把"核心零业务"做成 CI 断言的方案（eslint no-restricted-imports + Rust 目录守卫测试 + SlotLayout DOM 快照）。brief 的 P4 在 S3 这里不是承诺，而是会变红的门禁——这是评审最看重的"可验收性"。

3. **轻量与连续性的平衡点最好**。核心 ~15.5k 行（约 Polaris 的 10%），裁剪幅度真实可信；同时保留 Tauri 桌面形态与 React 原栈，不牺牲 Polaris 的产品身份（S4 的 -100% Rust 更彻底，但交付形态从桌面应用变成了纯 Web 应用；S9 的构建期插件则切断了运行时装插件的生态）。对"参考 Polaris 的轻量版"这个命题，S3 是"裁剪"而不是"改宗"。

4. **风险披露与对策达到了可排期粒度**。它对最大风险（chat 树残留宿主耦合）给出了"触碰 15~20 文件、M3 排 3~5 天专项"的具体量化，而不是"注意一下"式的敷衍；single 槽抢占、manifest 双端漂移、调度壳过薄也都有对应机制。

一句话总结我的票：**S4 赢在分数，S3 赢在"能落地成 Polaris 的正统 lite"——我会把票投给 S3。**
