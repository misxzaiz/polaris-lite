# 评委3评分表

> 评审视角：**产品与用户体验**。我最看重三件事：①「AI 对话交互布局不变」是否被真正保障（不是纸面声明，而是用户打开第一眼就能确认四段式——会话侧栏 + 消息流 + 底部输入区 + 面板区——与 Polaris 现状一致）；②插件化之后体验会不会退化（流式延迟、输入跟手、中断响应、消息渲染丰富度、主题一致性）；③桌面用户拿到手的第一个版本好不好用（开箱即用程度、安装形态、缺功能的可感知程度）。
>
> 评分独立完成，未参考其他评委。总分 = Σ(维度分 × 权重) × 10，归一到百分制。

**评语**：从产品视角看这是「布局不变」的最强保障——对话 UI 直接复制 worktree 里真实的 Polaris Chat 组件树（26,904 行），用户看到的不是"按 Polaris 布局重写的东西"，而就是 Polaris 本来的界面，交互零重学。插件清单（lite-chat/lite-settings/lite-history/lite-model）覆盖了首版可用的最小闭环，禁用插件回落空态引导卡的行为也与 Polaris 现状一致。2~4 人周的迁移估算让"第一个能用版本"到来最快。

**评语**：这是对 brief P2 回答得最"正面"的方案——核心就是四槽布局壳（sidebar/stream/input/panel 恰好对应 Polaris 四段式），分区尺寸、断点、主题 token 直接复制 Polaris Layout 现役值，并用 vitest 快照锁定 DOM 结构、SlotEmpty 复刻 ChatMainSlot 空态，布局不变性同时有"样式同源"和"测试锁定"双重保障。对话插件一次性认领四槽、跨槽协作收敛为插件内部状态，用户感知不到架构变化；single/stack 槽仲裁机制还顺带解决了"面板被抢占"这类体验事故。

**最大缺陷**：chat 树按槽拆入插件时需剥离对 appCoreBridge 21 个 store 的依赖，方案自估触碰 15~20 个文件、排期 3~5 天——若实际耦合更深，首版交付时间会滑档；此外四槽之外的表达力（如未来需要顶部工具条槽位）需改核心，扩展要过评审。

## 最推荐方案：S3 插槽容器

**理由（产品与用户体验视角）**：

1. **布局不变有双重保障，且答案最贴题**。brief P2 要求说明"布局骨架由谁提供、通过什么契约保证一致"。S3 的回答是十案中唯一把"布局骨架"本身做成核心产物的：核心 SlotLayout 四槽与 Polaris 四段式一一对应，分区尺寸/断点/主题 token 直接复制 Polaris Layout 现役值，再加 DOM 快照测试锁定、SlotEmpty 复刻 ChatMainSlot 空态——用户打开第一版看到的仍然是熟悉的 Polaris 对话布局，且这种一致不依赖"重写者手不抖"。

2. **插件化后体验不退代的路径最可信**。对话插件种子来自真实 Polaris Chat 树（worktree 26.9k 行），按槽拆入后跨槽协作是插件内部状态流，核心零感知；消息流、输入区、工具卡都沿用成熟实现而非重写。相比 S2/S6/S8/S10 的"重写 UI"路线，S3 把体验回归风险压缩到"chat 树去宿主耦合一处"，且给出了文件数与工期预估。

3. **第一个版本即可用性高**。插件清单覆盖对话主链路 + 设置/历史/模型/文件面板，cap 总线、审计、权限 gate 沿用 Polaris 已验证实现，M0~M6 每阶段有明确验收；核心约 15.5k 行（Polaris 的 10%），轻量目标与首版完整性的平衡在十案中最好。

4. **对体验的隐性保护**：single 槽仲裁（sidebar/stream/input 不被其他插件抢占）+ panel stack 槽多插件并存，恰好把 Polaris「对话常驻 + 面板随点随切」的交互模式制度化了，避免插件生态生长后出现布局被冲乱的体验事故。

**次选**：若团队更看重"第一个版本零风险、最快交付"，S1 是稳妥的次选（UI 完全是 Polaris 原装，迁移成本最低），可考虑以 S1 的 chat 插件化路径起步、把 S3 的槽位契约作为第二阶段的重构目标。同时建议冠军方案的落地版吸收两处他案优点：S2 的 layout-contract 文档化契约形态，以及 S9 的插件脚手架（plop 生成器）降低第三方插件作者的上手门槛。
