# 评委5评分表

> 评审视角：**真实裁剪幅度与成本核算**。重点核对各方案量化表与 `baseline.md` 第 6 节规模数据、总结杠杆点（最小核心约 6-8k 行）是否对得上，识别「把砍功能错算成轻量收益」「口径混用」「估算偏乐观」等问题。
> 核对基准：`src/` 49,794 行 / 279 文件；`src-tauri/` 101,032 行 / 250 文件；合计 150,826 行；chat-desk 23,763 行；worktree Chat 树 26,904 行；conversationStore 11,383 行 + session-v2 ~1,557 行；34 capability / ~30 cap id；36 commands；27 个非测试 store。
> 加权总分 = A×30% + B×25% + C×20% + D×15% + E×10%，归一百分制。

## S1 微核直译

| A 目标符合度 (30%) | B 可实现性 (25%) | C 轻量收益 (20%) | D 架构优雅 (15%) | E 迁移成本/风险 (10%) | 加权总分 |
|---|---|---|---|---|---|
| 7.5 | 9.0 | 6.5 | 5.5 | 8.5 | **74.8** |

**评语**：量化口径与 baseline 对得上——lite-chat ~40,000 行 = Chat 树 26,904 + conversationStore 11,383 + session-v2 1,557，分毫不差；后端 ≤42k 经逐目录 bottom-up 核算（router ~13k + ai_chat_core 3k + claude 1.8k + storage_exec 5k + plugin_service 2.9k + supervisor 2.2k + web 4.7k + proxy 5k…）基本可信，且诚实备注明确拒绝虚报「6-8k 微核」，态度端正。主要水分在前端：≤13k 行低估了 plugin-system(5.5k)+Common(3.7k)+Layout(2.6k)+services(~3.5k)+stores/hooks/types 的合计，bottom-up 约 18-22k，-74% 实际约 -60%。

**最大缺陷**：核心仍保留 proxy(5,039 行)——baseline 第 7 节自己已把 proxy 列为「明显是具体业务」，这与「核心零业务」硬约束直接冲突，属为保行为一致而留下的口径例外。

## S2 契约优先

| A | B | C | D | E | 加权总分 |
|---|---|---|---|---|---|
| 8.0 | 8.5 | 7.5 | 9.0 | 6.0 | **79.8** |

**评语**：核心 ≈9,000 行（6%）与 baseline 杠杆点 6-8k 精确呼应，且是十案中唯一连 AI 编排都出核的方案（ai-engine sidecar serves cap.ai.chat），核心零业务最纯粹；-83% 总账（29k/174.6k）算术一致，且把重写的插件代码如实计入总量而非藏起来。扣分点：bus+6 个内置 cap 压到 1,100 行偏紧（storage 会话 CRUD + fs 沙箱 + http 转发实测难低于 1.5k），chat-desk 从零重写 11k 行的工期未给总量估算，成本核算是本案最薄弱一环。

**最大缺陷**：通篇没有总工期/总人日估算——P0~P8 只有阶段依赖无工作量标注，而「重写 chat-desk 11k + ai-engine 2.2k + 8 插件 9k」约 22k 行全新代码的实际成本被留白。

## S3 插槽容器

| A | B | C | D | E | 加权总分 |
|---|---|---|---|---|---|
| 8.5 | 8.5 | 7.5 | 8.5 | 7.0 | **81.5** |

**评语**：量化是十案中少数经得起 bottom-up 复核的：核心 15.5k（10%）= 前端 6.5k（槽位系统+transport+theme+moduleLoader+4 store，逐项可加）+ Rust 9k（bus 700 + 9 caps + 插件三模块 + web），内部自洽；插件侧数字与 baseline 精确对表（Chat 树 26,904→18k、conversationStore+session-v2 ~13,000→7.5k），裁剪去向清楚，没有把「砍功能」混进「裁行数」——功能边界（单引擎+基础工具）是明说的。四槽 arity 把 Polaris 多贡献点体系收敛为可断言的注册制，布局不变性由核心 SlotLayout 锁定，是 P2 最硬的保证。

**最大缺陷**：除 M3（chat 树去耦 3-5 天）外各阶段均无工作量估算，总工期不明；且 chat 插件 25.5k 的裁剪幅度隐含较多功能删减，若验收按 Polaris 全功能对表会有落差。

| A | B | C | D | E | 加权总分 |
|---|---|---|---|---|---|
| 7.5 | 8.5 | 7.0 | 7.5 | 6.5 | **75.5** |

**评语**：量化表附了口径说明（Polaris 侧实测、lite 侧估算、验收 cloc 复核），是量化纪律最好的表述之一；核心 2.5k TS server + 8k 前端 bottom-up 基本可信，-84%/-100% 算术一致。水分点：两个引擎插件合计 1,200 行装下 Anthropic+OpenAI 双供应商流式+工具映射+中断，至少低估一半（现实 2.5-3k）；且「轻量收益」最大头来自整体放弃 Rust/桌面形态——这是换赛道而非同口径裁剪，README 已如实披露但量化表未单列这笔「形态收益」。

## S5 微前端

| A | B | C | D | E | 加权总分 |
|---|---|---|---|---|---|
| 8.0 | 8.0 | 6.0 | 7.0 | 6.5 | **73.0** |

**评语**：Rust 32k 的分项拆解（3.5+8+5+6+4+3.5+1.5）内部一致，但漏计 models/commands/lib/state 约 4-5k，实际约 36-37k；前端 9.5k 把 Common+Layout ~7k 瘦到 3.5k 偏乐观。致命的是工期：总计 10-13 人日覆盖「联邦运行时 + chat-desk 23.7k 行去 21-store 耦合 + 其余 7 个 remote + Rust 域删」，而其自己的风险表把 chat-desk 迁移评为「高」并设计了两步 compat-bridge——风险定级与工期估算自相矛盾，现实至少 15-25 人日。这是十案中量化与自述风险冲突最明显的一份。

**最大缺陷**：工期估算（10-13 人日）与自身风险披露（chat-desk 迁移=高风险、需 compat-bridge 过渡）严重不匹配；另 §6 说保留 Blob loader 兜底一个迭代、§8.3 又说放弃 Blob loader，前后矛盾。

**评语**：前端核心 ≤6k + 零 runtime 依赖是真裁剪，wc 化后 main/App/plugin-system/布局的压缩账大致可信。但两处量化经不起推敲：其一，Rust ≤55k 是十个方案里最胖的后端——ai/（含 simple_ai 10.1k）几乎原样保留，比 S1（42k）还多 13k，「轻量」主要靠前端撑门面；其二，chat-desk-wc ≤6k 与其自己的风险对策「迁移期允许 React in wc 包装现有子树」互相拆台——包装方案下 chat-desk 仍是 ~24k 行，6k 只有推倒重写才成立，而重写工作量在风险表里又被承认为最大风险。

**评语**：量化纪律十案最佳：P0~P7 每条删码都落到具体文件与实测行数，P3 -27,000（ai/ 21,513 + ai_chat_core 3,042 + capability 950 + 命令残尾）逐项可对上 baseline，阶段表求和 150,826-64,900≈85.9k 与 -44% 自洽，且明确区分「整目录删除下界 85k」与「目标形态 38k」两个口径——这种双口径诚实度值得肯定；前端终点 ~25k 也能 bottom-up 加出来。但后端终点「~13,000 行」与自己开列的树冲突：仅 router ~11k + plugin_service 2,904 + supervisor 2,169 + web 4,651 + config_store 1,175 就已 ~22k，全树实际 ~30-34k，头条数字 -75% 实际约 -60%。另：本方案在 Polaris 主仓开分支作业，与 brief P3「不是在 Polaris 上打补丁」、P8「不修改 Polaris 主仓任何文件」的硬约束相抵触（虽有 fork 兜底）。

## S8 事件溯源微核

| A | B | C | D | E | 加权总分 |
|---|---|---|---|---|---|
| 8.5 | 8.0 | 7.0 | 8.0 | 5.5 | **77.0** |

**评语**：量化标注「设计目标值、验收 cloc 实测」，诚实度好；替换对象核算准确（storage_exec 4,964 + conversationStore 11,383 → EventLog ~800 + checkpoint ~300，-92% 与分项一致；chat-projection 7k/23.7k = -70% 算术对）。但 Rust 4.5-6k 低估约 40%：流式引擎客户端（SSE 解析/工具调用/中断/重试）+ 分段日志（fsync/索引/tail 扇出）+ 双传输 web 桥 + checkpoint，bottom-up 约 7-9k；6 周工期对「从零造事件溯源基建 + 对话插件」偏乐观，虽已把「工程量低估」列为最大风险并给了退化预案。裁剪是真实的（消灭 conversationStore 与 21-store 桥），但属于「用新范式换行数」，不全是净减负。

| A | B | C | D | E | 加权总分 |
|---|---|---|---|---|---|
| 8.0 | 8.5 | 7.5 | 8.0 | 7.0 | **79.3** |

**评语**：核心 9,250 行（6.1%）与 baseline 杠杆点吻合，各包预算（bus 1.6k / server 3k / kit 0.9k / vite-plugin 0.35k）bottom-up 基本可信，-94% 算术一致；复用策略在重写派中最实在——壳组件、worktree Chat 四段子树、aiEvent 协议都是复制改造而非从零写，新写代码量比 S2 少一截。§11.1 对「运行时动态性损失」（不能热装插件、须 pnpm add + 重建）的披露是十案中最坦诚的取舍声明，并给了一条命令补偿与逃生舱接口。chat-desk 7k（从 26.9k 树裁 74%）偏紧但方向可信。

| 8.0 | 8.5 | 7.5 | 7.5 | 7.0 | **78.5** |

### 最推荐方案：S3 插槽容器（81.5 分）

从「真实裁剪幅度与成本核算」的评审视角，S3 在三件事上最让我信服：

1. **数字经得起复算**。核心 15.5k（前端 6.5k + Rust 9k）能按目录逐项加出来，不是拍脑袋的「6-8k 微核」也不是虚胖的 55k；插件侧 Chat 树 26,904→18k、conversationStore+session-v2 ~13,000→7.5k 与 baseline 实测数一一对应，裁掉什么、留下什么、功能边界收窄到哪里都有明示——没有把「砍功能」偷换成果「轻量收益」。
2. **裁剪结构与 baseline 的杠杆点判断同构**。baseline 指出最大杠杆是「对话域与业务面板已完成插件化的最后一公里」+「收窄 21-store 宿主桥」；S3 恰好只做这两件事：SlotHostApi 取代 appCoreBridge，chat 树复制入插件，核心退化成「四槽 + 一条总线 + 插件装卸器」。它没有为了好看去发明新范式（对比 S8 的事件溯源基建、S10 的渲染指令协议），因此估算里几乎不含「未知未知数」。
3. **风险集中在唯一一处且给了可执行的定价**。整个方案最难的部分被明确隔离为「chat 树去宿主耦合并预了工作量」，布局不变性由核心 SlotLayout 快照测试锁定，核心零业务由 eslint + Rust 目录守卫双闸锁死——承诺都有验收手段，而不是靠自觉。

次选：S9（若更看重插件分发与类型安全的长期收益）与 S2（若更看重契约纯粹性），但两者分别需要在「生态迁移成本」与「总工期核算」上补课后才可拍板。
