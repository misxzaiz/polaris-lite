# Polaris Lite 总纲（所有方案与评委的共同依据）

> 本文件是 polaris-lite 项目的唯一任务源。十份方案文档与评委打分都必须以本文件为基准。

## 一、用户原始目标（逐字）

> 参考polaris，在ai对话交互布局不变的情况下，产出一个轻量版的版本，核心不参与具体业务功能，前端面板和ai对话等由插件提供，需要提供十个各种实现方案的具体实现，注意按我的话拆分目标，使用子agent工作流投票打分，和polaris独立

## 二、按用户原话拆分的目标（P1~P7）

### P1 参考 Polaris
以现有 Polaris 仓库（Tauri + React + Rust，cap 总线 + 插件体系）为参照系。方案必须说明「相对 Polaris 现状，轻量版砍了什么、留了什么、怎么留」。基线事实见 `docs/baseline.md`。

### P2 AI 对话交互布局不变
轻量版的 AI 对话界面必须保持 Polaris 现有的对话交互布局：会话侧栏 + 消息流 + 底部输入区 + 面板区。布局结构、交互方式不重新发明。方案必须明确：布局骨架由谁提供（核心 or 插件）、通过什么契约保证插件提供的界面与原布局一致。

### P3 轻量版
产物是一个独立的、更小的版本：独立目录（本仓库 `polaris-lite`），可独立构建运行，不是在 Polaris 上打补丁。轻量 = 核心代码量、启动链路、依赖面显著小于 Polaris 现状（方案须给出可量化的裁剪目标，如核心保留目录清单、预估代码规模）。

### P4 核心不参与具体业务功能
宿主核心只保留通用平台能力：cap 总线（权限/审计/转发）、插件生命周期（发现/加载/启停）、会话与消息的存储契约、主题/i18n/窗口壳、AI 引擎调度接口。**所有具体业务功能（git、浏览器、各类业务面板、领域工具）一律不在核心**。方案必须给出核心目录白名单与业务黑名单。

### P5 前端面板和 AI 对话等由插件提供
对话界面本身也走插件化：核心提供「面板槽位/对话容器契约」，具体的对话 UI、消息渲染、输入框行为、业务面板都由插件注入。方案必须定义插件贡献 UI 的契约（如 contributes.views / panel slots / route 挂载点），并说明与 Polaris 现有插件体系的异同。

### P6 十个各种实现方案的具体实现
产出 **10 份不同的实现方案文档**，每份都是「具体实现」级别：包含架构图（文字图）、核心目录结构、cap/插件契约定义（含关键类型/接口签名）、AI 对话插件如何挂载、启动流程、与 Polaris 的复用/差异清单、裁剪量化目标、迁移步骤、风险。十份方案必须在**关键架构选择上彼此不同**（见第四节矩阵），不能是同一方案换皮。

### P7 子 agent 工作流投票打分
用子代理工作流完成：10 个方案作者代理并行写方案 → 5 个评委代理并行独立打分投票 → 汇总排名。评委维度与权重见第五节。最终产出 `docs/verdict.md`（得分表 + 每方案评语 + 冠军方案 + 后续落地建议）。

### P8 与 Polaris 独立
代码与产物全部放在 `D:\space\base\Polaris-lite`（或其子目录），**不修改 Polaris 主仓任何文件**；不依赖改动 Polaris 才能成立。可以**引用** Polaris 的代码作为起点/复制源，但轻量版自身可独立构建。方案须说明复用方式（复制 fork / 仅借鉴契约 / 依赖包引用）。

## 三、统一的硬性约束（每个方案都必须满足）

1. 对话交互布局 = Polaris 现状布局（会话列表侧栏 + 消息流 + 输入区 + 面板区）。
2. 核心零业务：核心目录里不得出现具体业务功能模块。
3. AI 对话 UI 与业务面板均为插件，通过统一契约挂载。
4. 保留 cap 总线思想：统一权限/审计/转发通道（可简化，但不可退化为组件直调后端）。
5. 前端技术栈可自选，但须说明与 Polaris（React+Zustand+Vite）的迁移成本。
6. 每份方案给出：架构图、目录树、核心契约（TS/Rust 接口签名级）、插件清单、启动流程、裁剪量化表、迁移步骤、风险与对策。
7. 与 Polaris 的关系：明确哪些文件直接复制、哪些重写、哪些放弃。

## 四、十方案的差异化矩阵（每方案认领一格）

| # | 代号 | 核心形态 | AI对话UI提供方式 | 插件机制 | 前端栈策略 |
|---|------|----------|------------------|----------|------------|
| 1 | S1 微核直译 | 复制 Polaris 壳，删业务 | 复用 Polaris Chat 组件为首个内置插件 | 沿用 Polaris plugin-system 原样 | React+Zustand 原栈 |
| 2 | S2 契约优先 | 重写极薄核心，只留总线+生命周期 | 对话 UI 按 Polaris 布局重写为插件 | 新设计最小 contribute 契约 | React 原栈 |
| 3 | S3 插槽容器 | 核心只提供布局槽位（sidebar/stream/input/panel 四槽） | 对话插件填四槽 | 槽位注册制 | React 原栈 |
| 4 | S4 Web-Only 单进程 | 砍 Tauri，Web 服务器 + 浏览器 | 对话 UI 插件 + HTTP/SSE 总线 | 进程内插件注册表 | React 原栈 |
| 5 | S5 微前端 | 核心是布局壳 + module federation | 每面板/对话是远程微前端模块 | 模块联邦 + 生命周期协议 | React，模块化加载 |
| 6 | S6 Web Components | 核心框架无关，面板=自定义元素 | 对话 UI 为 wc 插件 | customElements 注册 | 框架无关（可混栈） |
| 7 | S7 渐进剥离 | 直接在 Polaris 上分阶段剥离成 lite 配置 | Chat 组件逐步插件化 | 沿用现有体系+剥离清单 | 原栈渐进 |
| 8 | S8 事件溯源微核 | 核心=事件日志+投影，UI 全是投影插件 | 对话=会话事件流的投影插件 | 投影订阅制 | React 原栈 |
| 9 | S9 Vite 插件化模板 | 核心=脚手架模板，业务全在模板外插件包 | 对话模板插件即装即用 | npm 包+脚手架生成 | React+Vite 模板 |
| 10 | S10 桌面双进程 | Rust 极简壳（窗口+总线）+ Node/JS 插件宿主进程 | 对话插件跑在宿主进程渲染 | IPC 总线 + 插件进程 | React 原栈 |

## 五、评委打分维度（5 评委 × 10 方案）

每位评委对每个方案按 5 维度打分（每维 1-10 分），并给出 1-3 句评语：

| 维度 | 权重 | 说明 |
|------|------|------|
| A 目标符合度 | 30% | 是否满足 P1~P8 全部硬性约束（布局不变、核心零业务、UI 插件化、独立可构建） |
| B 具体可实现性 | 25% | 契约/目录/流程是否落到可开工粒度，技术选型是否成立 |
| C 轻量收益 | 20% | 相对 Polaris 的裁剪幅度是否真实、量化是否可信 |
| D 架构优雅/可维护 | 15% | 边界清晰度、契约稳定性、长期演进成本 |
| E 迁移成本/风险 | 10% | 从 Polaris 复用与迁移的现实成本，风险是否被如实披露 |

总分 = Σ(维度分 × 权重)，归一到百分制。评委互相独立，不得参考他人评分。
