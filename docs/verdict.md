> 评审日期：2026-11-18。方法：5 位评委代理（工程落地 / 架构演进 / 产品体验 / 安全治理 / 成本核算五种视角）独立读完 brief + baseline + 十份方案，按 5 维度加权打分（A 目标符合度 30% / B 可实现性 25% / C 轻量收益 20% / D 架构优雅 15% / E 迁移成本 10%）。评委互相独立、未见彼此评分。各评委完整评分见 `docs/judging/judge-1.md ~ judge-5.md`。

## 二、冠军方案：S03 插槽容器

**一句话**：核心 = 一个只提供 `sidebar / stream / input / panel` 四槽的布局容器 + cap 总线；AI 对话插件一次填满四槽，业务面板按槽位注册。对应 Polaris 现状四段式对话布局，布局不变性由核心 `SlotLayout` + DOM 快照测试锁定。

**五位评委给出的推荐理由（去重后）**：
1. **核心零业务做成 CI 门禁而非自觉**（J1/J2/J5）：eslint `no-restricted-imports` + Rust 目录守卫测试双闸，是十案中唯一把 P4 约束工程化的方案。
2. **最小门面真正拆除最大耦合点**（J2）：`SlotHostApi`（dispatch/stream/listen/emit/config/kv/i18n/theme）替代 Polaris `appCoreBridge` 的 21-store 全局泄漏；s3.1 manifest 是 Polaris 契约的瘦身版而非另起炉灶，迁移是「复制 + 收口」。
3. **布局保真有双重保障**（J3）：四槽与 Polaris 四段式一一对应，对话插件种子直接取自 Polaris worktree 的真实 Chat 树，体验回归风险最小。
4. **数字经得起复算**（J5）：核心目标 ~15.5k 行（前端 6.5k + Rust 9k，约为 Polaris 15.08 万行的 10%），逐目录对账、无虚报。
5. **保留桌面形态与 React 原栈**（J1）：是「裁剪」而非「改宗」，第一周即可见四槽壳运行。

**已知短板（落地时必须处理）**：
- 沿用了 Polaris 的 Blob-URL 插件加载器（155 行，无沙箱边界）——评委建议作为独立工作项替换或加固；
- 安全视角（J4）：插件仍为同窗同特权执行，权限 gate 强制力依赖插件自觉，与 Polaris 现状水位相同；若要真实隔离，可借鉴 S10 的 Worker/进程隔离作为后续演进；
- 跨槽协作依赖插件内部 store，需要防止插件间隐式状态耦合。

## 三、各方案一句话判决（评委意见合并）

| 方案 | 判决 | 关键短板 |
|------|------|----------|
| S01 微核直译 | 开工最快、风险最低的保底路线；但核心仍内嵌 ai_chat_core/proxy 等业务实现，「核心零业务」达成度垫底 | 核心 55k 行偏大；Blob 加载无沙箱 |
| S02 契约优先 | 契约最小化教科书（17 类贡献点瘦身为 4 类），安全评委第一名；代价是 UI 与 AI 引擎全量重写 | 无总工期估算；重写面最大 |
| S03 插槽容器 | **冠军**：四槽容器 + 槽位注册制，零业务有 CI 门禁，布局不变有快照锁定 | Blob loader 待加固；同特权插件 |
| S04 Web-Only 单进程 | 轻量化最彻底（Rust 归零、-84% 前端），工程确定性高；但把桌面 AI 工作台变成浏览器页面，偏离 Polaris 产品身份 | 丢桌面能力；产品形态改变 |
| S05 微前端 | 对 Blob 加载器诊断准确；但为 155 行加载器的问题引入整套 Module Federation 运行时，复杂度收益不成比例 | 共享依赖治理复杂；工期估算自相矛盾 |
| S06 Web Components | 框架无关理念最纯、长期互操作性最好；但放弃全部 React 资产做全量 wc 重写，23.7k 行对话 UI 重写风险最高 | 成本收益错配；后端裁剪最少（55k） |
| S07 渐进剥离 | 执行清单最扎实、每步可验证、风险披露最好；但工作发生在 Polaris 主仓并合回 main，与 P8「与 Polaris 独立」硬约束正面冲突 | 违反 P3/P8；量化口径前后不一（85k vs 38k） |
| S08 事件溯源微核 | 「日志即真相」架构最优雅、审计能力天然最强；但需先从零造 EventLog/投影/检查点全套基建，交付周期最长 | Rust 预算低估 ~40%；每 token 持久化有渲染延迟风险 |
| S09 Vite 模板 | npm 包 + 构建期集成最正统，上手体验最好；但插件从「运行时可装卸」降级为「npm 依赖」，运行时插件生态断裂 | 动态性损失；150+ 存量插件迁移成本未计价 |
| S10 桌面双进程 | 唯一提供真实进程级隔离的方案（安全评委认可）；但自研 UINode 渲染指令协议是隐藏工程黑洞，每 keystroke 跨进程往返伤对话跟手度 | 渲染指令协议=高频演进契约，5 年稳定性风险最高 |

## 四、评委共识与分歧

**共识（5/5 或 4/5）**：
- S07 渐进剥离虽工程质量好，但违反「与 Polaris 独立」的硬约束，不能作为主选；
- S03/S02/S04/S09 是四个值得保留的候选方向；
- 任何方案都要补上「同特权插件」的安全短板（除 S10 外）。

**分歧**：
- S04 是否因「丢掉桌面形态」而一票否决：J2 给 87（第 2），J3/J5 给 77/75（第 5/6）。若产品定位允许纯 Web，S04 立即上升为强力候选。
- S10 的进程隔离价值：安全视角视其为唯一真隔离（第 4），产品视角视其为体验灾难（第 10）。若未来把安全隔离列为第一优先，S10 的 Worker 隔离设计值得单独抽取。

## 五、落地路线建议

1. **主干**：按 S03 插槽容器开工——先复制 Polaris Layout 壳裁成四槽 SlotLayout + SlotRegistry，再复制 plugin-system 收口出 `SlotHostApi`，chat 插件从 worktree Chat 树按槽拆入。
2. **吸收**：
   - 从 S02 吸收 layout-contract 文档化契约与「契约单源 + 运行时 schema 校验」（补 Polaris 已知缺口）；
   - 从 S09 吸收插件脚手架（plop 生成器）降低新插件成本；
   - 从 S04 吸收 SSE `Last-Event-ID` 事件续传设计（web 模式复用）；
   - 从 S10 保留「Worker 隔离」作为后续安全演进项。
3. **验收门**（贯穿全程）：SlotLayout DOM 快照测试（布局不变）+ eslint no-restricted-imports / Rust 目录守卫（核心零业务）+ 每阶段 `tsc --noEmit` 与 `cargo check` 绿灯。
